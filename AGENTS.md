# Agent Notes

- Keep this library reusable. Runtime source must not contain host-specific gameplay concepts.
- Two layers, two entries. The root entry (`src/index.ts` → `game-core`) is renderer-agnostic: never import or bundle renderer packages into it. The Pixi Ready UI kit (`src/pixi/` → `game-core/pixi`) may import `pixi.js`, but only as an external optional peer dependency (never bundled), and it may import the root entry as **types only** — the host passes its `UiRuntime`/`MotionRuntime` instances in. `scripts/check-pixi-build.mjs` enforces this after every build.
- Do not create rendering applications, DOM nodes for particles, timers, tickers, or `requestAnimationFrame` — in either layer. Kit views animate only through `MotionRuntime` and settle taps only through `ButtonController`/`WindowController`.
- The one exception is `ReadyUiOverlay` (`src/pixi/ReadyUiOverlay.ts`, `createReadyUiOverlay` in `game-core/pixi`): the host infrastructure for games that are NOT drawn with Pixi may create one transparent Pixi `Application` and its own overlay DOM (layer, canvas, hit layer, safe-area probe) inside the container it is given. It stays host-driven — `overlay.update(frameMs)` is the only clock, Pixi's app / system / shared tickers never run on their own, and it creates no `requestAnimationFrame`, timer, `ResizeObserver` or `window` / `document` listener (`scripts/check-pixi-build.mjs` checks the bundle). Input policy is native DOM hit testing on its own hit layer (`pointer-events` / `clip-path`), never synthetic or re-dispatched events, never a restyled host element. It owns no game state and imports no runtime: `core` / `ui` come in as structural `{ update }` / `{ isBlocking }` options. Do not grow it into a screen manager or router. Verify with `npm run showcase:overlay` (installed Chrome).
- The second exception is `OrientationGuard` (`src/pixi/OrientationGuard.ts`, `createOrientationGuard` in `game-core/pixi`), the "rotate the device" cover of a portrait-only game. Opt-in: `orientation: 'portrait'`; the default `'any'` creates nothing. It owns one `position: fixed` cover element, that element's input listeners (they swallow what hits the cover) and ONE `MediaQueryList` `change` listener on `(orientation: landscape) and (pointer: coarse)` — no user-agent sniffing, no pixel threshold, no timer, no `window` / `document` listener; a desktop (fine primary pointer) is never blocked, whatever its size. It blocks input only and never pauses the game (Contract V1 `setPaused` has no arbitration between a modal, an ad and this cover): the host pauses from `onChange` / `blocked`. Verify with `npm run showcase:orientation` (installed Chrome, touch emulation).
- Host integrations provide surfaces, nodes, textures, asset loading, render calls, and frame timing.
- Root modules that reason about wall time (`OfferRuntime`) take the clock injected (`input.now()`, unix seconds from the host's server-anchored time); never read `Date` or `performance` inside `src/`. `frameMs` only paces work. `src/offers/` is a 1:1 port of Trail Arrow's `OfferChain.ts` — change its semantics only with a spec update; the kit (`src/pixi/`) never imports it.
- Analytics goes through `AnalyticsRuntime` (`src/analytics/`) only: the transport, context, queue store and clock are injected; no endpoint-specific code outside `hazarTransport.ts`, no global `fetch`, no storage, no lifecycle listeners in `src/`, and never a real JWT anywhere in this repository (tests use a fake token, the showcase a fake transport). Runtimes never import each other — Core-owned behavior is instrumented at composition level (`src/composition/`, type-only imports); gameplay adds game-specific events.
- Real-money purchases go through `PurchaseRuntime` (`src/purchases/`) only: the payments adapter, the granted-token registry and the rewards are injected; no platform SDK or SDK global, no storage, no timers (SDK timeouts live in the adapter, restore waves in the host), no prices and no reward kinds (`coins`, `lives`, `no_ads` …) in `src/`. Never grant before the platform answered ok, and never let a consume stand between a mark and its grant (spec §10, production 0.1.31): claim (already granted? + mark, one synchronous block) → grant → consume, NOT awaited, for a direct purchase under either policy; restore per receipt, never waiting for another receipt — `before-consume` = claim → grant → consume, `after-consume` = consume → claim → grant (the only grant that waits, for its OWN consume) — and do not "improve" this financial behavior further: change it only with an approved spec update. Ledger mode (`options.ledger`, spec §11) is the production-safe path for consumables: the value OWNER's `apply` writes the effect + token in one durable write (never a check-then-apply pair), Core consumes only after `applied` / `already_applied`, never after `not_durable` (fail closed — no grant, receipt kept); keep the legacy path unchanged and call it best-effort, never claim exactly-once for it. The one consume policy is `productKinds` (host config): a `consumable` (the default) is that pipeline unchanged, an `entitlement` (a permanent right — SoliPix `no_ads`) is never consumed on either path, is still granted once per token, answers `RestoreResult.owned` instead of a `duplicate` on later passes and sends no revenue when restored; never name a product id in `src/purchases/`, and do not grow this into subscriptions, expiry or server receipts. It imports neither `OfferRuntime` nor `AnalyticsRuntime`; `src/composition/purchaseAnalytics.ts` and the host's `onEvent` are the link. Tests and the showcase use a fake adapter — never a real SDK request.
- Ad eligibility goes through `AdsRuntime` (`src/ads/`) only, and it only DECIDES: the config, the state store and the input (clock, level, NO_ADS, payment sums, currency scale, local calendar) are injected; never an advertising SDK call, a storage, `Date` or a timer in `src/`. It is a 1:1 port of Trail Arrow's `AdsGate` — segments, check order, calendar day / hour counters, global cooldowns, NO_ADS not blocking rewarded, the rule-less `default` segment = no ads; the donor issues listed in the spec (B1–B12) are kept on purpose, so do not "fix" eligibility: change it only with an approved spec update. Ad tables (`segments.tsv` / `placements.tsv`) are game data — Core ships the parser and the validator, tests use verbatim donor copies in `tests/ads/fixtures/`. It imports no other runtime; `src/composition/adsAnalytics.ts` and `purchaseAds.ts` are the links. The per-game layer over it is the Ads Policy (`src/ads/policy.ts`): gameplay reports a placement (`requestInterstitial('level_complete')`) and never holds an ad condition; the policy gates (kind switch, placement allow-list, NO_ADS switches, in-flight, first-show delay, session cap, cadence, cooldown floors, per-placement caps) run BEFORE the tables and can only add refusals, never grant what the tables refuse — keep it that way. Placement ids stay generic strings; `resolveAdsPolicy` merges in depth and never mutates a preset. `TRAIL_ARROW_AD_POLICY_V1` (`src/ads/presets.ts`) is the donor tables verbatim with every knob neutral, pinned by a differential test against `{ config }` — a number change there is a production ad change: bump its version, and do not make it the default until the user says so. V1.1 (`TRAIL_ARROW_AD_POLICY_V2`, `noAds.offerAfterInterstitials`, `timeouts`): the NO_ADS offer trigger is raised by the runtime and TAKEN by the host (`consumeNoAdsOffer()`) — the runtime never decides which window to show or when; the watchdog numbers are data the host reads (`getRequestTimeouts`) — never add a timer, a pending flag or a window state to `src/ads/`.
- Platforms go through the Platform Layer (`src/platform/`) only, as capabilities: `identity / environment / storage / gameplay` required, `ads / payments / lifecycle` optional — a platform that cannot leaves the capability undefined, never add a stub that pretends and never grow one giant adapter. The production target is EXPLICIT (the host builds the platform for its build); no SDK detection in `PlatformRuntime`. A storage read that failed must reject — never answer an empty profile; the local mirror / rollback guard / `save_seq` stay in the host. `PlatformPayments` extends `PaymentsAdapter` — do not create a second payments interface; `PlatformAdResult.rewarded` is the only reward signal and Core never calls a show method. No SDK global, DOM, `localStorage`, `Date`, timer or `fetch` in `src/platform/` (the DEV platform's store is injected; SDK timeouts, watchdogs and catalog retry schedules belong to adapters / hosts). `GamePlatformConfig` is client-safe: no secret-bearing field types (`appSecret`, `serviceKey`, `privateKey`, `secretKey` …), a JWT only as `jwtRef`. Tests and the smoke (`npm run smoke:platform`) use the DEV platform — never a real SDK, payment or network.
- Platform SDK adapters never enter the root bundle: each is its own public entry (`game-core/platform/yandex` ← `src/platform/adapters/yandex/`, built by `vite.platform-yandex.config.ts`) that imports the root as TYPES only; `src/platform/support/` belongs to those entries and is never imported by a root module. Do not relax the root guard for an adapter — `scripts/check-platform-build.mjs` adds to it. An adapter is a 1:1 port of production: keep the donor's timeouts (every awaited SDK call goes through `withTimeout`), retries, guest mode (`getPlayer({ scopes: false })` by default, the same request object at boot and in every retry), write throttle, ad watchdog and latch, and the issues listed in its spec; `storage.set` answers `true` only for a CONFIRMED write that carried the call's patch (never "queued" — the one donor issue fixed on purpose, see `PlatformStorage.set`); never grant a reward on `onClose` alone, never answer an empty profile for a failed read or a guest, never call `registerShown` / mark tokens / keep a save mirror in an adapter — the game's ECS, sound and analytics come in as hooks. The SDK global is named in one file (`sdk.ts`); tests and the smoke (`npm run smoke:platform-yandex`) inject a fake SDK and fake / compressed timers — never the real SDK.
- Save orchestration goes through `SaveGate` (`src/save/`), and it only GATES: one initial `storage.get` per read group of `profile.save` (`groups`, else every key; the Core record `<profile.id>.core` rides with the first group), `loaded` / `missing` (read ok, nothing stored = a new player) / `failed` (never written for the gate's lifetime), writes refused (`not_open`) until the host applied the load and called `open()`, one `storage.set` per write, results `{ ok, reason }` instead of throws. Core state lives only under the Core record key, never inside a game key. It never reads the game's save format, migrates, keeps a mirror, merges cloud / local or guest / player, retries or times out — those stay in the host / gameplay; no timer, clock or global in `src/save/`. It relies on the `PlatformStorage.set` PATCH contract: an adapter whose SDK replaces the whole object must merge before a second key is ever written.
- A core-owned soft currency goes through `SoftCurrencyWallet` (`src/economy/`) only, and it only COUNTS: its state is the SaveGate Core record `wallet` (`{ v: 1, balance, rewardedLevels }`) — never a game key or a second save path; a failed Core read or a record that is not a V1 wallet makes it `unavailable` (balance `null`, every change refused) — never fall back to `startBalance` there; changes are refused until the wallet is loaded and the gate is open, amounts are integers ≥ 0, results are answered, never thrown. Level rewards: a first completion is paid once per level identity (persisted), replays pay only through the profile's opt-in `replayReward`, fails never; Core never reads game metrics or holds a reward number. It does not own a gameplay-owned currency, several currencies, prices, shops, purchase / offer orchestration, timers or UI — it imports types only.
- Core-owned lives go through `LivesRuntime` (`src/lives/`) only, and it only COUNTS: its state is the SaveGate Core record `lives` (`{ v: 1, lives, regenStart, attempt? }`) — never a game key or a second save path; a failed Core read or a record that is not a V1 lives record makes it `unavailable` (lives `null`, every change refused, nothing written) — never fall back to `startLives` or a free refill there. Every number is the host's `LivesConfig` (`maxLives`, `startLives?`, `regenSeconds`, `refundOnWin`); never put a product number or rule (a price, free levels, unlimited lives, a level-1 reset) in `src/lives/`. Regeneration is computed from the stored stamp and the injected clock on every call (whole periods → lives up to the cap, the remainder carried; at the cap no period runs; a clock behind the stamp re-anchors the period, never takes a life) — no `setInterval`, no timer, no global. One logical attempt = one life: one attempt runs at a time (`startAttempt` pays once, `endAttempt` ends once), the open attempt is durable in the same record — spend + open is ONE write, end (+ refund) + close is ONE write — and a run the gameplay restored after a reload is continued with `resumeAttempt()` (no spend, no write), never paid again; a stored attempt that was not resumed is abandoned by the next `startAttempt` (no refund). Never key an attempt by the level number; the host picks the spend moment and tells new / restored / restart apart. It never shows ads, sells, charges coins or opens windows: grants come only after a confirmed delivery, and it imports types only.
- Use TypeScript strict mode and preserve the public `FxSurface` boundary.
- Add or update Vitest coverage before changing runtime behavior. Kit tests run headlessly through `tests/pixi/setup.ts`; visual checks go through the showcase (`npm run showcase`) with Playwright on the installed Chrome (`npm run showcase:shots`), never the sandboxed in-app browser (no WebGL).
- Ready UI art lives in `assets/pixi-ui/` (extracted from Trail Arrow). Never read assets from `../trail_arrow/` at runtime; never copy anything from `reference-vlad-bubbles/`.
